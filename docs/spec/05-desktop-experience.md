# Desktop user experience

**Status:** first-release interaction specification.

## Navigation

First launch is a focused **Sign in with Azure DevOps** screen. The action uses the installed Azure CLI and Microsoft system-browser sign-in. After account and organization setup, workspace navigation is **Work items** → **QA Queue** → **Runs**. **Settings** is a separate, bottom-anchored sidebar action so it is visually distinct from the workflow. Settings contains account connection, named ADO run profiles, provider configuration and local-data controls. Sidebar text and icons use responsive sizing with readable minimums across desktop and compact window layouts.

The selected account, organization and project are always visible in the header. Switching project does not mix work-item IDs or reports across organizations. Keyboard and screen-reader users can complete every primary flow.

## Connect and choose work

1. **First launch:** explain read-only Azure DevOps access and show **Sign in with Azure DevOps**. Azure CLI opens Microsoft sign-in; no app-owned client ID is needed. Show missing CLI, missing account, success, access denial and cancellation clearly.

Disconnect opens an OS-native choice to cancel, keep local QA data, or delete it. It leaves the machine-wide Azure CLI sign-in intact. Deletion removes queued work items and snapshots, run history/reports/contracts, encrypted evidence, Azure DevOps profiles/type mappings and saved run targets; it preserves provider settings unless the user separately clears those credentials in Settings.
2. **Choose organization/project:** list organizations available through Accounts List where discovery succeeds; offer a validated organization name/URL as fallback. Check project-read access before saving. Remember validated choices per signed-in account. List accessible projects and remember the selection per account. Selecting a project automatically discovers its teams and creates a local default profile using the project-matching team, or the first available team. Existing projects without a profile get the same setup on startup.
2a. **Run profiles:** Settings can store multiple validated profiles per CLI account for users who need to select a different team or board scope. Each profile includes organization, project, team, target sprint board column and Story IDs. The normal work-item flow does not require creating or importing a profile; project/team setup is saved locally by the app.
2b. **Sprint scope:** The searchable sprint picker is always shown on the Work items screen. It loads the selected team's iterations automatically and remains visible with an empty option list when the project has no sprints. Active Requirement types are discovered from Azure DevOps work item categories, with standard type names as fallback. Expanding a Requirement shows its child Tasks and each task's column in the selected sprint board; tasks absent from that board are labeled accordingly. The ID/title filter searches loaded Stories and Tasks. A multi-select taskboard-column filter beside it filters only child Task rows, keeping parent Stories visible. Combining both filters uses AND for Tasks; matching the parent Story keeps all of its Tasks eligible for the column filter. Place **Hide Tasks** after the expanded task rows and keep the selected-items Add action in a fixed footer while selection is active. Work-item type mapping controls and config-file import are not part of the normal setup UI.
3. **Search:** input accepts numeric ID or title phrase; filters include state/type and optionally area/iteration. Results show actual ADO type, title, ID, state, revision and parent. Selecting a Requirement/Story shows its acceptance criteria and expandable child Tasks. Add the Requirement, chosen Tasks or both to the local queue; do not update ADO.
4. **Queue:** group entries by organization/project. Render each queued Story as the main row with its queued child Tasks nested below as separate rows; keep standalone Tasks visible in an Other queued work section. Show revision and stale/inaccessible markers. Remove and reorder. Queue order affects presentation, not verdict priority. A Task informs scope but does not prove parent acceptance criteria.

## Configure and run

1. **Target:** choose local repository, ADO Git ref/PR, development/staging URL, or both. Show commit identity, dirty-tree state and URL origin. Never guess which PR or deployment corresponds to a requirement.
2. **Target setup:** select a local or ADO Git repository and optional dev site. No repository config file or JSON editing is required for the supported automatic path: if the root `package.json` has a `test` script, the app adds `npm test` as a diagnostic command and shows it in the plan. Dependency installation stays disabled because the Repository worker has no network access. Exact JUnit testcase mappings are still required before Repository evidence can verify an Acceptance Criterion. Browser-only users can proceed without a repository config or container. Advanced users can optionally save custom commands and mappings in encrypted app settings.
3. **AI configuration:** every user must configure a supported provider and save compatible model entries. Settings offers provider-specific credential import and a keyboard-accessible searchable model catalog. Saving a model automatically sends a minimal plain prompt; each saved row shows green **Test Success** or red **Test Fail**, with a **Retest** action. The check succeeds when the selected provider/model returns text. Credential changes invalidate test state. Run setup permits only a saved model whose latest test succeeded; that one model is used by the Orchestrator, specialists and Reviewer. Save/retest controls disclose provider charges and, for Claude Code, plan-allowance use. Claude Code settings confirm connection with the connected account email when available. No provider-free QA run is available. Settings also lets users create, update and remove named browser test accounts. Credentials are write-only in the renderer; only labels, origin and whether username/password are present are shown after save.
4. **Prepare the plan:** after refreshing selected ADO revisions, show the provider/model and exact selected work-item IDs, revisions and fields that will be sent for synthesis. Include run-specific instructions and disclose that work-item text is untrusted provider context. The user can remove context or stop. The explicit **Prepare agentic plan** action sends the disclosed selection to the Orchestrator before opening Plan Review. No worker starts at this stage.
5. **Review the plan and run envelope:** the Orchestrator reads each selected Story and Tasks together. It treats a Story as feature context, not as an independently tested item, and proposes a feature summary, source-linked acceptance criteria and verification for each selected Task. The review distinguishes ADO text from generated proposals, surfaces ambiguity/conflicts, and lets the user edit, accept or reject proposals and scenarios. Then show repository paths, target origin, selected account labels, command/tool permissions, worker limits and conservative cost estimate. Run instructions are bounded and may not contain credentials. Final run approval freezes accepted QA scope and is required before workers start; out-of-envelope requests pause for approval.
6. **Agentic plan and diagram:** the approved Orchestrator plan delegates to the selected repository/backend and/or browser/frontend specialists using the selected tested model. The diagram shows the Orchestrator, selected agents, result types, and post-run Reviewer before the final summary. It is generated from validated assignments and updated to show completion or blocking.
7. **Preflight and run:** validate refreshed source revisions, target, browser/container, disk space, selected tested model, selected account existence/origin, cost reservation and limits. Show streamed Claude Code response text while it synthesizes the plan, generates the approved delegation/scenarios/tests, and reviews evidence. Specialists generate repository tests and bounded Playwright scenarios from the approved context; ordinary app code routes those outputs only to approved command IDs and isolated workers. A run may open a separate visible Playwright Chromium window when explicitly selected; headless remains default. The post-run Reviewer checks bounded source/test code and direct observations. Persist Orchestrator, specialist, Reviewer, Scenario and Browser-step progress; live model response text is displayed locally and is not retained in run history. Cancellation, provider errors and budget exhaustion retain partial results. Repository output and Playwright evidence appear beside accepted criteria.

## Report and history

The report opens with both execution state and verdict, plus the reason each follows policy, followed by the actual delegation diagram and criterion coverage table. Each row exposes source behavior, required layer, assigned agent, scenario/test status, direct observations and artifacts. The Reviewer Agent summary links each criterion assessment to direct observation IDs, and its generated-test code-review notes cite exact paths and lines. Reviewer output cannot change the deterministic verdict. Ordered Playwright screenshots are previewable in the report; restricted traces and raw files remain behind the export warning. Every failure/block has the operation/stage, safe diagnostic category, observed detail, concrete next action, retryability and available restricted evidence; true failed assertions also show expected and actual behavior. A separate section lists omitted, unverified and blocked work with reasons and provider usage/cost estimate. Users can export HTML/Markdown/JSON, compare with previous run, rerun using a newly approved envelope, or delete the run and artifacts.

## App identity

Use the supplied `apps/desktop/build/icon.png` for the macOS/Windows package icon, native window identity where supported, favicon and sidebar brand. Keep the product name `Agentic QA` consistent in window titles, installer names, and user-visible copy. The standard QA browser is a separate Playwright-managed window, not embedded in the Electron renderer.

Exports are previewed for restricted artifacts and redaction status. ADO publishing is absent in the first release; an export is a local file the user chooses to share.

## Error copy requirements

Errors name the failed operation, whether it affected the run verdict, and a concrete next action. Examples: “This organization is not available to the signed-in account. Check the organization name or sign in with another account.” “This app build is missing its Azure DevOps sign-in configuration. Contact the app administrator.” “Repository checks could not start because the container runtime is unavailable. Site checks can still run.” “The site redirected to an unapproved origin. Add it to the approved auth flow or choose another target.” Never show raw tokens, provider payloads or stack traces in ordinary UI errors.

## Visual and accessibility requirements

- Use a consistent readable type and control scale, clear spacing and hierarchy, and visible keyboard focus across every screen.
- Windows and macOS use the same renderer and styles. Keep UI changes shared across both platforms and verify them with equivalent viewport size, display scaling and work-item/profile data; document any intentional native-only difference.
- Support an 800px-wide desktop window without horizontal page scrolling on first-run, organization/project, work-item and queue screens.
- Keep loading, empty, error and disconnected states clear; every primary flow remains keyboard-operable and screen-reader labeled.
